# Планирование: анализ, идентификация проблем и поиск решений

## Существующие и потенциальные проблемные места

- БД имеют только один инстанс
- Ручной деплой
- Нет автоматических E2E тестов
- Отсутствие тестов на CI сильно задерживает релизы
- CRM Api и Shop API ходят в одну БД
- Из-за перегруженности системы сообщения в RabbitMQ могут теряться

## Инициативы

- Настроить мониторинг и логирование системы
- Проаналазировать нагрузку, найти узкие места
- Настроить шардирование и кластеризацию БД
- Реализовать паттерн Backpressure, чтобы сообщения не терялись
- Нанять AQA инженера
- Покрыть код автоматическими E2E тестами
- Релизовать CI/CD для автоматической доставки и тестирования кода
- Выделить отдельные БД для CRM Api и Shop API
- Настроить браузерное и серверное кэширование

## Приоритеты

1. Реализовать паттерн Backpressure, чтобы сообщения не терялись
   - Простой механизм, который позволит системе работать более стабильно, пока ведутся другие работы
2. Выделить отдельные БД для CRM Api и Shop API
   - Известное узкое место системы. Разделение БД должно ускорить ее работу.
3. Настроить браузерное и серверное кэширование
   - Хороший способ как улучшить пользовательский опыт, так и снизить нагрузку на сервер.
4. Настроить мониторинг и логирование системы. Проаналазировать нагрузку, найти узкие места
   - Без этого пункта невозможно будет улучшать систему и реагировать на ошибки в режиме реального времени.
5. Покрыть код автоматическими E2E тестами (Нанять AQA инженера)
   - Очень много времени тратится на ручное тестирование кода, автоматические тесты сильно улучшат ситуацию.
6. Релизовать CI/CD для автоматической доставки и тестирования кода
   - Автоматическое тестирование на этапе сборки и автоматическая доставка кода заметно ускорят релизы.
7. Настроить шардирование и кластеризацию БД
   - Хороший способ повысить стабильность и скорость работы системы.

## Какой вы видите целевую архитектуру через полгода

Система покрыта логами и мониторингом. Код доставляется и тестируется автоматически посредством CI/CD. Каждый сервис работает со своей БД, для них настроены шардирование, кластеризация, репликация. Все запросы к системе кэшируются (в качестве кэша можно использовать Redis).

## Три пункта за полгода

1. Реализовать паттерн Backpressure, чтобы сообщения не терялись
2. Выделить отдельные БД для CRM Api и Shop API
3. Настроить браузерное и серверное кэширование

Все три пункта относительно дешевые в разработке, но могут дать приличный рост производительности.
